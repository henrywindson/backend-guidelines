Backend Coding Standards

Node.js · Express · ORM (Prisma / Sequelize / TypeORM) · SQL database  •  A reusable convention set for any service

This document describes how to write server-side code: how to split it into layers, what to name things, how to validate input, how to return data, and what to think about before you call a feature done. It is written to be tech-based, not project-based — apply it to any Node/Express service you work on.

1. How to use this document

  • MUST NOT — doing this breaks the system or fails code review. No exceptions.
  • SHOULD — the expected way; deviate only with a written reason in the pull request.
  • TIP — helpful, not mandatory.
The rule that beats all others

Consistency wins over cleverness. Before writing anything new, open the closest existing feature and follow its shape. Code that looks like the rest of the codebase is easier to read, review and fix than code that is individually smarter. If you believe a convention is wrong, change it everywhere through a discussion — never in one file.

2. Core principles

PrincipleWhat it means in practice
One job per layerA file that routes should not query. A file that queries should not know about HTTP.
Fail fast, fail loudlyValidate config at startup and input at the edge. A wrong value should crash the boot, not corrupt data at 3 a.m.
One way to do each thingOne response helper, one error class, one pagination helper, one logger. Alternatives are technical debt.
Explicit over implicitName what a function does. Pass what it needs. No hidden globals, no magic strings.
Never trust the clientIdentity, tenancy and permissions come from the verified token — never from the request body.
Small, boring functionsIf you cannot see a function on one screen, split it. Reviewers approve what they can read.

3. Architecture

Use a modular monolith: one deployable service, split internally into self-contained business domains. Each domain owns its routes, its HTTP handling, its business logic and its data access. Domains talk to each other through service functions, never by reaching into another domain's database tables.

Why this shape

It gives you the clarity of microservices (clear boundaries, easy to find code) without the cost (network calls, distributed transactions, multiple deploys). If a domain later needs to become its own service, it lifts out cleanly because the boundary already exists.

│   ├── validate.middleware.js

├── routes/

│   └── v1/                  # /api/v1 aggregator per audience (public, user, admin)

tests/                       # mirrors src/ — unit + integration

Rules

  • Folder names are lowercase; module folders are singular (order/, not orders/).
  • utils/ holds pure helpers only. If a helper needs the database, it is a service, not a util.
  • Nothing outside config/ reads environment variables or constructs clients.
  • Tests mirror the source tree, so a reader can find the test for a file without searching.

5. Module anatomy

Every module contains the same set of files. Same names, same order, every time — so any developer can open an unfamiliar domain and know exactly where to look.

FileResponsibilityMay import
order.routes.jsURL paths, middleware chain, API doc annotationsrouter, middlewares, controller
order.controller.jsRead the request, orchestrate services, send the responseservices, utils, error classes
order.service.jsBusiness rules and database accessORM client, other services, utils
order.validations.jsInput schemas for body / query / paramsthe validation library only
order.schema.jsAPI documentation schema objectsplain objects, generated input schemas
Tip

Add a scaffold script (create:module) that generates these five files. It removes the temptation to "just put it in the controller for now", which is how layered architectures die.

6. Layer responsibilities

LayerJobMust not
RouteMap a URL and HTTP verb to a middleware chain and one controller functionContain logic or database calls
MiddlewareAuth, validation, rate limiting, uploads, error shaping, request contextKnow about one specific business domain
ControllerRead req, translate shapes, call services, send resQuery the database; hold business rules
ServiceBusiness rules + all data accessTouch req/res; know about HTTP status codes*
DataPersist and retrieveBe reached from anywhere but a service

* Services may throw a shared application error that carries a status code. They must not write to the response.

Never

Never query the database from a controller. If the service function you need does not exist, write it. A controller holding a query is the single most common architectural violation, and it spreads fast: the next person copies it.

7. Request lifecycle

  Client
    │  JSON body (API casing)
    ▼
  1. app entry        security headers · CORS · body parser · compression · request id
    ▼
  2. route group      rate limiter  →  version + audience prefix (/api/v1, /admin/v1)
    ▼
  3. module route     authenticate  →  authorize  →  validate(schema)  →  controller
    ▼
  4. controller       translate input  →  call service(s)
    ▼
  5. service          business rules  →  database  →  return domain objects
    ▼

    ▼
  7. response layer   uniform JSON body out

  Anything thrown  →  async wrapper catches  →  error middleware  →  uniform JSON error

Steps 4 to 6 are where most of your code lives, and most of this document is a detail of those three steps.

8. Naming conventions

Files

TypePatternExample
Module file<entity>.<layer>.js, entity singular camelCaseorderItem.service.js
Middleware<name>.middleware.jsvalidate.middleware.js
Job<name>.job.jscleanup.job.js
UtilcamelCase; PascalCase for exported classescaseConverter.js, ApiError.js
Test<source>.test.js at the mirrored pathtests/unit/services/order.service.test.js

Functions — the verb identifies the layer

Pick one verb set per layer and never mix them. A reader should know which layer a function belongs to from its name alone.

LayerVerbsExamplesDo not use
Controllerget · create · update · delete getOrders, getOrderById, createOrder, updateOrder, deleteOrder fetch, find, handle, process, do
Servicefetch · add · modify · remove fetchOrders, fetchOrderById, addOrder, modifyOrder, removeOrder get, create, update, delete
Event handlerhandlehandleOrderPaidanything else

Semantics: fetch reads, add inserts, modify updates, remove soft-deletes. Reserve a distinct name such as deleteOrderById for a genuine permanent delete, so the dangerous operation never hides behind the everyday one.

Everything else

  • Variables and parameters: camelCase. Booleans read as a question: isActive, hasAccess, canEdit.
  • Module-level fixed values: UPPER_SNAKE_CASE — const MAX_PAGE_SIZE = 100;
  • Classes: PascalCase. Database columns: snake_case (see the next section).
  • No abbreviations that are not universal: request not rq, organisation not org — but id, url, api are fine.
  • No magic values in logic. if (status === 'in_progress') becomes if (status === ORDER_STATUS.IN_PROGRESS).

9. Case convention boundary

Databases and APIs usually disagree about casing. Pick one convention for each side and one place where they meet. The recommended split, and the one used throughout these examples:

WhereConventionExample
Database columns and ORM modelssnake_caseuser_id, created_at, is_active
Service arguments and return valuessnake_caseaddOrder({ user_id, total_amount })
HTTP request body and querycamelCase{ userId, totalAmount }
HTTP response bodycamelCase{ orderNumber, createdAt }
Realtime event payloadscamelCase{ orderId, status }
Validation and API doc schemascamelCasematches what clients send and receive
The boundary rule

The controller is the only place that converts between the two. Services speak one language only. Two recursive helpers — keysToSnake() and keysToCamel() — do the work; nobody hand-writes conversions.

WRONG
// snake_case leaking into the controller
const user_id = getUserFromToken(req);

// hand-built database-shaped object
await addOrder({
    user_id: userId,
    total_amount: total,
});

// conversion inside a service
export const addOrder = (data) =>
    db.order.create({ data: keysToSnake(data) });
CORRECT
// camelCase everywhere in the controller
const userId = getUserFromToken(req);

// convert once, at the boundary
await addOrder(
    keysToSnake({ userId, totalAmount: total }),
);

// service speaks one language only
export const addOrder = (data) =>
    db.order.create({ data });
  1. No snake_case variable names in a controller.
  2. Build camelCase objects and convert at the call, including filters and partial updates — not just the request body.
  3. Never write an already-converted key inside the converter call.
  4. Sort values that name a database column (sortBy=created_at) are values, not keys — they stay as-is.

10. Routing rules

  • Version every API from day one: /api/v1/.... Adding v2 later without v1 is painful.
  • Separate audiences by prefix — for example /api/v1 for regular users and /admin/v1 for elevated ones. Different audiences get different auth middleware, so keeping them apart prevents accidental exposure.
  • Resources are plural nouns; actions are HTTP verbs. GET /orders, POST /orders, GET /orders/:id, PATCH /orders/:id, DELETE /orders/:id. Avoid /getOrders or /orders/delete.
  • Sub-resources nest one level at most: GET /orders/:id/items. Deeper than that, use a query filter instead.
  • Middleware order is fixed: 
    router.post('/', rateLimiter, authenticate, authorize, validate(schema), upload, controller);
  • Mount open (unauthenticated) routes before the blanket authentication middleware, and everything else after it. A route on the wrong side of that line is either broken or a security hole.
  • One route file per module; the aggregator only mounts prefixes and never contains logic.

11. Validation layer

Every request that carries client data is validated before the controller runs. Not "most requests" — every request, including internal and admin ones.

export const createOrderValidation = {
    body: Joi.object({
        productId: Joi.string().uuid().required(),
        quantity: Joi.number().integer().min(1).max(999).required(),
        note: Joi.string().max(2000).allow('', null).optional(),
    }),
};

export const getOrdersValidation = {
    query: Joi.object({
        ...paginationQuerySchema,          // page / limit / sortBy / orderBy
        status: Joi.string().valid(...ORDER_STATUSES).optional(),
    }),
};

Rules

  • One exported object per endpoint, named <action><Entity>Validation, holding any of body, query, params.
  • Keys use the API casing, because they describe what the client sends.
  • Strip unknown keys. Anything not in the schema must never reach the controller — that is what stops mass-assignment bugs.
  • Return all errors at once (do not abort on the first), so the client can fix the whole form in one round trip.
  • Shape belongs here; rules belong in the service. "Must be a UUID" is validation. "This order must belong to you" is a business rule and needs the database.
  • Reuse shared fragments (pagination, id params, date ranges) instead of redeclaring them per module.

12. Controller layer

export const createOrder = asyncHandler(async (req, res) => {
    const userId = getUserFromToken(req);
    const { productId, quantity, note } = req.body;

    const product = await fetchProductById(productId);
    if (!product) throw new ApiError(HttpStatus.NOT_FOUND, 'Product not found');

    const order = keysToCamel(
        await addOrder(keysToSnake({ userId, productId, quantity, note: note || null })),
    );

    res.sendResponse({
        statusCode: HttpStatus.CREATED,
        data: order,
        message: 'Order created successfully',
    });
});

Rules

  • Wrap every async controller in the shared async wrapper so rejected promises reach the error middleware. You should almost never write try/catch in a controller.
  • End with the shared response helper. Never call the raw JSON method directly — a single helper is what keeps the API envelope identical across hundreds of endpoints.
  • Throw the shared error class with an explicit status code. Never throw a bare Error.
  • Identity and tenancy come from the verified token, never from the payload.
  • Keep it thin. Roughly 60 lines is a smell; the excess is usually business logic that belongs in a service.
  • No database calls, no ORM imports, no SQL.

13. Service layer

export const fetchOrders = async (userId, pagination = {}, filters = {}) => {
    const { skip, take, sort } = pagination;
    const where = { user_id: userId, deleted_at: null, ...filters };

    const [items, total] = await Promise.all([
        db.order.findMany({ where, skip, take, orderBy: sort }),
        db.order.count({ where }),
    ]);

    return { items, total };
};

Rules

  • A service never sees req or res. If it needs the request, the boundary is in the wrong place.
  • Return domain data ({ items, total } for lists). Shaping for the client is the controller's job.
  • Always fetch the count alongside the page in one Promise.all — two sequential round trips for one list is waste.
  • Wrap multi-table writes in a transaction. If two writes must both succeed, they must share a transaction.
  • A service may call another module's service. Keep dependencies one-directional; if two services import each other, extract the shared piece.
  • Guard reads and writes by ownership inside the service, so no caller can forget.

14. Database & ORM

Schema conventions

  • Tables plural snake_case (order_items); models singular PascalCase (OrderItem); columns snake_case.
  • Primary keys are UUIDs unless there is a strong reason for auto-increment (sequential ids leak volume and are guessable).
  • Every table has created_at and updated_at. Anything a user can delete also has deleted_at.
  • Ownership columns (created_by, updated_by, deleted_by) make audit questions answerable later.
  • Index every column you filter, sort or join on — especially the tenant/owner key and created_at. Add composite indexes matching real query patterns, for example (user_id, created_at).

Query rules

  • Soft deletes: every read on a soft-deletable model filters deleted_at: null. Forgetting it resurrects deleted records in the UI, and it is a bug reviewers should catch on sight.
  • Select what you need. Do not load whole rows (and their relations) to read two columns.
  • No N+1 queries. Use the ORM's include/join instead of querying inside a loop.
  • Never build SQL by string concatenation. Use the ORM or parameterised queries — this is the SQL-injection rule.
  • Every schema change ships as a migration, reviewed like code. Never push schema changes straight to a shared database.
  • Migrations must be backwards compatible with the currently deployed code: add a nullable column first, backfill, then enforce.

15. Middleware

Middleware is for anything cross-cutting — work that many routes need and no single domain owns.

MiddlewarePurpose
Response helperAttaches the standard response function to every response. Mounted first.
Request idAssigns a traceable id and puts it on every log line for that request.
Security headers, CORS, body limitsApplied globally, before routing.
Rate limiterGlobal limit plus a stricter one on auth and other abusable endpoints.
AuthenticationVerifies the token and attaches the caller to the request.
AuthorizationChecks permissions for the specific resource and action.
Actor resolverNormalises "who is acting" into one shape used by every controller and audit write.
ValidationRuns the schema, strips unknown keys, rejects with a readable message.
UploadFile type and size limits, storage handling.
Not-found + error handlerMounted last. Convert everything into the standard error envelope.

Writing one

  • Signature (req, res, next), or a factory (options) => (req, res, next) when configurable.
  • On failure call next(error). A middleware that writes its own response bypasses the error handler and produces a differently-shaped body.
  • Attach results under a clearly named property and document it at the top of the file.
  • Keep it synchronous unless it truly needs I/O; every middleware runs on every matching request.

16. Responses & errors

One envelope for everything

res.sendResponse({
    statusCode: HttpStatus.CREATED,   // defaults to 200
    data: order,                      // defaults to null
    message: 'Order created successfully',
});

A single envelope means client code never guesses the shape, and error handling on the frontend can be written once.

One error class for everything

throw new ApiError(HttpStatus.NOT_FOUND, 'Order not found');
throw new ApiError(HttpStatus.FORBIDDEN, 'You do not have access to this order');
StatusUse when
200 / 201Success; 201 specifically for "a resource was created"
400Malformed input, or a business rule the client can fix
401No token, expired token, invalid token
403Authenticated but not allowed — wrong owner, missing permission
404Resource does not exist or is soft-deleted
409Conflict — duplicate email, version mismatch, already processed
422Well-formed but semantically invalid
429Rate limit exceeded
500Never thrown deliberately — it means an unhandled bug
Error message rules

Messages are user-facing. Write "Order not found", not "findFirst returned null". Never leak stack traces, SQL, internal ids or library names to a client. Log the technical detail; return the human sentence.

Use 404 rather than 403 when revealing existence itself is a leak — for example, another tenant's record.

17. Pagination & filtering

  • Every list endpoint is paginated. No exceptions, including "small" tables — small tables grow.
  • Pick one pagination style for the whole service and use shared helpers. Mixing offset and cursor pagination across endpoints forces every client to implement both.
  • Standard parameters: page, limit, sortBy, orderBy, with defaults applied by the validation schema (for example page=1, limit=10, newest first).
  • Cap the page size (100 is a reasonable maximum). Without a cap, ?limit=1000000 is a denial-of-service button.
  • Whitelist sortable fields. Passing a raw client string to an orderBy is an injection risk and a performance trap.
  • Return a consistent envelope: the items plus { page, limit, total, totalPages }.
  • Filters are explicit query parameters, validated like everything else. Never accept an arbitrary "where" object from a client.

18. Auth, permissions and tenancy

Authentication

  • Short-lived access tokens (minutes) plus a longer-lived refresh token. Never issue a token that does not expire.
  • Refresh tokens are stored hashed and rotated on use. A reused refresh token means theft — revoke the family.
  • Passwords are hashed with a slow algorithm (bcrypt/argon2). Never log, echo or email a password.
  • Verify the token's signature, expiry, issuer and audience — not just that it decodes.

Authorization

  • Model permissions as flat strings such as resource:action:scope, checked by a reusable middleware. Avoid scattered if (user.role === 'admin') checks — roles change, permission checks then rot silently.
  • Check permission at the route and ownership in the service. Route-level checks answer "may this role do this?"; service-level checks answer "may this user do it to this record?".

Tenant / owner isolation

The rule that prevents the worst class of bug

The tenant or owner id used in a query comes only from the verified token — never from the body, query or URL. Accepting it from the client lets one customer read another customer's data, which is a breach, not a bug report.

Every scoped query includes the owner key in its where clause. When loading by id, verify ownership before acting. Put that check in one shared helper so it is impossible to write it slightly differently in twenty places.

19. Configuration & environment variables

Never

process.env is read in exactly one file. Everywhere else imports a validated config object. Direct reads scattered through the codebase are how a typo becomes undefined at runtime instead of a startup crash.

WRONG
const ttl = process.env.TOKEN_TTL;         // string, maybe undefined
const isProd = process.env.NODE_ENV === 'production';
const port = process.env.PORT || 3000;      // default duplicated everywhere
CORRECT
import config from './config/env.js';

const ttl = config.jwt.accessExpiresIn;     // validated, typed, defaulted
const isProd = config.env === 'production';
const port = config.port;

Rules

  1. Validate at startup with a schema: types, allowed values, defaults, required flags. A missing variable must crash the boot with a clear message — never fail silently at request time.
  2. Every new variable goes into .env.example in the same commit, under the right section, with a placeholder or default. That file is the contract for anyone setting the project up.
  3. Never commit real secrets. Placeholders only: SECRET=change-me or an empty value.
  4. Group config by concern (config.db, config.jwt, config.aws) so imports read clearly.
  5. No environment checks scattered through business logic. If behaviour differs per environment, express it as a config flag (config.features.x), not as if (env === 'production') deep in a service.

20. Logging & audit trail

logger.info({ orderId, userId }, '[Order] created');
logger.warn({ ip, email }, '[Auth] failed login attempt');
logger.error({ err, orderId }, '[Order] payment capture failed');
  • Never console.log. Use the shared structured logger so logs are filterable, levelled and machine-parsable.
  • Prefix messages with a context tag ([Order], [Auth], [Webhook]) and pass structured fields as an object — not string concatenation.
  • Include the request id in every line so one request can be traced end to end.
  • Log levels mean something: error = needs a human; warn = suspicious but handled; info = a significant business event; debug = development detail.
  • Never log secrets or personal data — no tokens, passwords, card numbers, full request bodies containing them.
  • Log every security decision: permission denied, rate limit hit, origin rejected, token refused.

Audit trail

For actions that change data a user could later dispute, write an audit record: who, what, when, on which resource. Make audit writes fire-and-forget with a caught error — an audit failure must never fail the user's actual operation, and never block the response.

21. API documentation

  • Document endpoints where they are defined, as annotations next to the route. Documentation in a separate wiki always drifts.
  • Generate request schemas from the validation schemas so docs cannot contradict what the server accepts.
  • Define response schemas as named, reusable objects and reference them, rather than inlining a schema in every route.
  • Name schemas <Domain><Purpose>: OrderResponse, PaginatedOrderResponse, OrderCreateInput.
  • Document error responses, not only the happy path — clients need to know what a 409 means here.
  • An endpoint without documentation is not finished.

22. Background jobs & scheduling

  • Anything slow, retryable or non-essential to the response belongs in a job, not in the request path — emails, exports, third-party sync, cleanup.
  • Jobs live in their own folder, one file per concern, and call the same services the controllers use. No duplicated logic.
  • Make jobs idempotent. They will run twice at some point; running twice must not double-charge or double-send.
  • In a multi-instance deployment, guard scheduled work with a distributed lock, or every instance runs it simultaneously.
  • Log start, finish and item counts. A silent job is impossible to debug when it stops running.
  • A job must never crash the process: catch, log, continue to the next item.

23. Realtime (WebSocket)

  • Authenticate the connection during the handshake, exactly as you would an HTTP request, and rate-limit events per socket.
  • Event names follow a stable pattern: <domain>:<event>. Client-to-server events are actions (order:create); server-to-client events are facts (order:created).
  • Handlers are named handle<Event> and delegate to the same services as HTTP. Never duplicate business logic between the two paths.
  • Broadcast into rooms scoped to an owner or resource — never to all connected clients.
  • Payloads use the same casing convention as the REST API, converted at the handler boundary.
  • Across multiple instances, use a shared adapter (for example Redis) so a message published on one instance reaches sockets on another.

24. Security checklist

  1. Validate all input and strip unknown fields — this closes mass-assignment and most injection vectors.
  2. Parameterised queries only. No string-built SQL, ever.
  3. Owner/tenant scoping from the token on every scoped query.
  4. Rate limit authentication, password reset, OTP and any expensive endpoint.
  5. Security headers and a restrictive CORS allowlist; never reflect an arbitrary origin with credentials enabled.
  6. Body size limits on JSON and uploads; validate file type and size, and never trust the client-provided filename or MIME type.
  7. Secrets in environment variables only — not in code, comments, tests, fixtures or commit history.
  8. Short token lifetimes; do not extend them for convenience. Hash refresh tokens at rest.
  9. No sensitive data in URLs (they land in logs and browser history) or in error messages.
  10. Verify webhooks by signature before trusting the payload.
  11. Keep dependencies current; run an audit in CI and treat high-severity findings as blocking.
  12. Principle of least privilege for database users, cloud keys and service accounts.

25. Performance

  • Fix the query before adding a cache. Most "slow API" reports are a missing index or an N+1 loop.
  • Paginate everything; cap page size; never load a full table into memory.
  • Run independent async work concurrently with Promise.all, sequential work only when there is a real dependency.
  • Cache what is read often and changes rarely (config, permissions, reference lists). Always set a TTL, and invalidate on write — a cache with no invalidation strategy is a bug with a delay.
  • Do not block the event loop: no synchronous file or crypto work on the request path.
  • Enable compression and set sensible timeouts on every outbound call, so one slow third party cannot exhaust your workers.
  • Measure before and after. "It feels faster" is not a result.

26. Testing

TypeYou mockYou assert
Controllerthe service layerservices called with the right arguments; correct status code and response shape; error paths forwarded
Servicethe database clientthe query filters, data and ordering; soft-delete filters present; ownership enforced
Middlewarerequest/response objectspasses through, or rejects with the right status
Validationnothingrequired fields, enums, formats, boundary values
Integrationthe database or external servicesthe real middleware chain end to end for critical flows
  • Tests never touch real infrastructure — no live database, cache, queue or third-party API. They must run offline and in any order.
  • Keep mock factories in one shared helper file rather than redefining them per test.
  • Test names describe behaviour: "returns 403 when the order belongs to another user", not "test order 3".
  • Cover the unhappy paths — permissions, not-found, conflicts, invalid input. Happy-path-only suites give false confidence.
  • When you change a source file, update its test in the same commit. A stale test is worse than no test.
  • Every bug fix gets a test that fails before the fix and passes after it.

27. Formatting & imports

  • A committed formatter config is the only style authority. Never override it locally, and never reformat unrelated lines — it buries your real change in noise.
  • Enable format checking and linting in CI so style is never a review topic.
  • Named imports only; avoid wildcard imports, which hide what a module actually uses.
  • Import order: runtime built-ins → third-party packages → internal shared modules → local files.
  • No unused imports, variables or commented-out code. Version control remembers deleted code; the file should not.
  • Comment the why, not the what. // increment counter is noise; // counter is per tenant, so the row is locked inside the transaction saves the next reader ten minutes.
  • Prefer async/await over promise chains; never mix both in one function.
  • Guard clauses over nested conditionals — return early and keep the happy path at the left margin.

28. Building a feature — the order of work

  1. Model — add or change the schema, write the migration, add indexes, decide on soft delete.
  2. Scaffold the module's five files so the layering exists before the code does.
  3. Validation — schemas for create, update and list, reusing shared fragments.
  4. Service — data access and business rules, with ownership checks and soft-delete filters.
  5. Controller — thin orchestration, boundary conversion, standard response.
  6. Routes — the middleware chain in the fixed order, mounted in the right audience group.
  7. Permissions — add the permission strings and gate the routes.
  8. Docs — request and response schemas, including error cases.
  9. Tests — controller, service and validation at minimum; integration for anything money- or auth-related.
  10. Observability — log the significant events, add an audit record for state changes.
  11. Self-review against section 29 before requesting a review from anyone else.

Raw JSON response callthe shared response helper, so the envelope stays uniform
